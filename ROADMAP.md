# Soundboard — Roadmap

Planned features and feature proposals. [`DESIGN.md`](DESIGN.md) describes the app as it is; this file describes where it is going.

## How a feature goes from idea to code

1. **Proposal.** The feature gets a section under [Proposals](#proposals): what it does, how it changes the design (naming the `DESIGN.md` sections affected), open questions, and a step-by-step implementation plan.
2. **Review.** The project owner reviews the proposal and answers its open questions. Work starts only once it is approved.
3. **Implementation.** One step at a time, test-first, one commit per step, each passing `npm run check`.
4. **Design update.** `DESIGN.md` is updated to describe the new behavior, in its own commit, reviewed like any design change. The proposal is then removed from this file, and its backlog entry too, if it had one.

### Proposal template

```markdown
### <Feature name>

**Goal.** What the user can do afterwards, in a few sentences.

**Design changes.** What changes, section by section of DESIGN.md (§n.n).

**Open questions.** Decisions the owner needs to make, each with a recommended answer.

**Plan.**
1. <step> — <what is tested>
2. …
```

## Proposals

### Waveform

**Goal.** An open track in the playlist dialog shows its waveform above the Start and end slider, so the owner can see where the quiet intro or the long tail is when choosing the points, and sees the playhead against the music while the track plays. Waveforms are generated by the browser in the background after startup, one at a time, and stored by the server, so each file is decoded once ever. The header shows the progress and has a button to stop.

**Design changes.**
- **§2.1 / §1.1 (layout, constraints).** The server creates a hidden `.soundboard-cache/` directory in the audio root. The scanner already ignores names starting with `.`; the document says the cache is disposable and may be deleted at any time.
- **§5.1 (domain model).** New `WaveformStore` (`src/library/waveform-store.js`): reads, writes and lists the stored waveforms. One file per audio file, at `.soundboard-cache/waveforms/<id>.wf`, in this format:
  - A 16-byte header: magic `SBW1`, the bucket count (u16), the source file's size (u32) and its modified time in seconds (u32).
  - Then `bucketCount` pairs of signed bytes: the minimum and maximum sample in each bucket, scaled to −127..127. All channels are mixed down by taking the extreme of each bucket across channels.
  - 1024 buckets for every file, whatever its length: 2 KB plus header. A 4-hour library of 1000 files is 2 MB. A bucket is about 0.3 s of a 5-minute track. That is plenty for a dialog about 600 px wide drawn at twice the pixel density.
  - A waveform is **stale** when the source file's size or modified time no longer matches the header. Stale ones count as missing and are overwritten when regenerated.
- **§5.2 (HTTP API).** Three endpoints, none of which touch playback state:
  - `GET /api/waveforms` → `{ "missing": ["Combat/1.mp3", …] }`: every sound and track with no current waveform, sounds first, then tracks in playlist order.
  - `GET /api/waveforms/<id>` → the raw `.wf` bytes (`application/octet-stream`, `Cache-Control: no-store`), `404` when there is none or it is stale.
  - `PUT /api/waveforms/<id>` → body of raw bytes, at most 4 KB; checks the magic, that the length matches the bucket count, and that the id is a known file (`404` otherwise). The server fills in the size and modified time itself, from the file on disk, so the browser only sends the peaks. `400` for a malformed body, `413` for a longer one.
- **§6.1 / §6.2 (facade, events).** Commands `startWaveforms()` and `stopWaveforms()`; events `waveforms.progress { done, total, running, failed }` and `waveform.ready { id }`. A query `getWaveform(id) → Promise<Waveform | null>` (peaks as a `Int8Array`), cached for the few waveforms an open dialog needs. `start()` begins generation by itself once the library has loaded.
- **§6.3 (ports).** New `WaveformDecoder` port, `decode(url, signal) → Promise<Int8Array>` with a fake for tests. It returns the finished 1024 pairs, so the decoded audio never leaves the adapter.
- **New `logic/waveform-service.js`.** Owns the queue: asks the backend what is missing, then for each id decodes, uploads, emits progress, and moves on. One at a time, with a short pause between files so playback is never starved. A file that fails to decode or upload is counted in `failed`, skipped and not retried until the next page load. Stopping lets the current decode finish, then idles; starting again asks the backend for the missing list afresh. Generation state is not remembered across a reload: F5 starts it again.
- **New `logic/peaks.js`.** The pure part: reduce a list of channels of samples to min/max byte pairs per bucket. Unit-tested.
- **New `audio/waveform-decoder.js`** (adapter, not unit-tested, listed in the manual checklist). Fetches `/media/<id>`, decodes it with `OfflineAudioContext.decodeAudioData` created at a low sample rate (the browser resamples while decoding, so a 5-minute stereo track is about 10 MB at 8 kHz instead of 100 MB), reduces it with `peaks.js`, and drops the buffer before returning.
- **§9.1 (layout).** A small indicator in the header, left of the volume controls, only while generating or when something failed: "Waveforms 12 / 87" with a thin progress bar and a ■ button that stops it (a ▶ button starts it again). Updated through inline styles and text.
- **§9.7 (Customize dialog).** `RangeControl` gets an optional waveform: a `<canvas>` above its bar with the same horizontal scale as the bar, so the handles line up with the sound. A new pure `ui/waveform-draw.js` maps peaks to canvas bars and is unit-tested; the canvas drawing itself is not. It is drawn once, at the control's size and the device pixel ratio, again only on resize, and in a muted version of the dialog's accent. The part outside the handles is dimmed by the same overlay the bar uses. While the waveform is not available the control looks as it does today.
- **§10 (project structure), §11 / TESTING.md, §12 (memory).** The new files; manual checks for generation, the header indicator and the drawing; the memory note: a decode is reduced to peaks at once, so at most one low-rate decoded track (about 10 MB) exists at a time.

**Open questions.**
1. *Sounds too?* Do sounds get a waveform above their start and end slider? **Recommended: yes.** They are short and cheap, they are the most useful case (cutting silence off a sample), and the same service handles them. They would be generated first.
2. *Player bar.* Should the player bar's progress bar also show the waveform? **Recommended: no.** It is thin and shared by up to six bars, and it would mean a fetch per playing track. The dialog is where the points are chosen.
3. *Resolution and amplitude.* 1024 buckets, linear amplitude. **Recommended: keep it.** Quiet tracks look flat on a linear scale; the drawing could normalize to the track's own peak. Recommended: normalize, so a quiet file still shows its shape.
4. *Decode sample rate.* 8 kHz is the lowest the Web Audio spec requires, but Safari may round up. **Recommended: ask for 8000 Hz and accept whatever the browser gives**; peaks at any rate look the same.
5. *Pausing while audio plays.* Generation starts by itself once the splash closes, as decided. Should it also pause while something is playing? **Recommended: no.** It is one low-rate decode at a time, and pausing would leave a long session without waveforms. The stop button covers the rest.
6. *Where to keep the cache.* `.soundboard-cache/` in the audio root, next to the options files, so it travels with the library. **Recommended: keep it.** The alternative, a directory under the user's home, would not follow a library moved to another machine.

**Plan.**
1. `peaks.js` — min/max bucketing: mono and stereo, fewer samples than buckets, silence, scaling to bytes, clipping at ±1.
2. `WaveformStore` — write then read back, header checks, stale on a changed size or mtime, listing what is missing in sounds-then-tracks order, rejecting a wrong length or magic, ignoring unknown ids.
3. HTTP endpoints — `GET` list and file, `PUT` with its `400`, `404`, `413` and `405` cases, against a temp copy of the fixture.
4. `BackendApi` methods and `WaveformService` with a fake decoder and fake backend — queue order, progress events, one at a time, failures skipped and counted, stop and restart, no retry of a failed id.
5. `Soundboard` facade — commands, `getWaveform` caching, auto start after `start()`.
6. `audio/waveform-decoder.js` and its wiring in `main.js` — manual check in the browser.
7. Header indicator — manual check.
8. `waveform-draw.js` and `RangeControl` canvas, in the track accordion and, if question 1 is a yes, the sound dialog — manual check.
9. `DESIGN.md` update and removal of this proposal and backlog entry 13.

## Backlog

### Planned, in the owner's order

These are the next features, in roughly the order they will be built. Each will get its own proposal when its turn comes. **Decided** lists the owner's answers already given; the notes list what else is known and the questions still to settle.

**Decided for all of them.** Customization changes apply immediately and are saved with a 500 ms debounce, as the sound Customize dialog does (DESIGN.md §6.4, §9.7). Re-sorting on screen waits until the dialog closes. Playback state is never remembered across a page reload, so F5 always gives a clean start.

#### 13. Waveform

The track's waveform drawn above its progress bar and start/end points.

- **Decided:** waveforms are generated in the browser, which is the only place that can decode audio without a third-party library.
  - Once the splash closes, the page asks the server which waveforms are missing and generates them one at a time in the background.
  - The header shows that this is happening, with progress and a button to stop it.
  - Each finished waveform is sent to the server, which stores it, so a track is only ever decoded once.
- **Research for the proposal:** the storage format and drawing method that keep memory low.
  - A fully decoded 5-minute stereo track is about 100 MB, so each decode must be reduced to peaks straight away and the decoded audio dropped before the next one starts.
  - The likely answer is a fixed number of min/max pairs per track stored as bytes, which is a few KB each, in a hidden directory such as `.soundboard-cache/`. They would be fetched only when a dialog shows them and drawn on a `<canvas>`.
  - The work must not starve playback on the 8 GB MacBook. Decoding at a low sample rate with an `OfflineAudioContext` may help.
  - Open: do sounds get waveforms too, above their start and end slider (DESIGN.md §9.7)?

### Later, unordered

#### Rescanning while running

Pick up added or removed files without restarting, by a button or by watching the directory.

- **Seam:** `BootstrapService` and the scanner are reusable; the page reloads the library through `/api/library`.
- **Notes:** the nested-directory and metadata questions currently happen in the terminal; while running they would need an answer from the UI or a non-interactive rule.

#### LAN access and phone remote control

Open the app on a phone on the same network to choose what plays, while the PC does the playing.

- **Seam:** commands and events are plain serializable objects and every command goes through `dispatch()`, which validates it (DESIGN.md §6). The server holds no playback state.
- **Notes:** would add a `--host` option, a `GET /api/events` stream (server-sent events) and a `POST /api/commands` relay, plus a "player" and "remote" role for pages.

#### Search, filter and keyboard shortcuts

- **Seam:** UI only, built on the existing facade.

#### More saved preferences

- **Seam:** `.soundboard` settings, `SettingsStore` and the `/api/settings` endpoints (DESIGN.md §2.3, §5.2).

#### Context menus on touch screens

Long press to open a tile's menu.

- **Seam:** the shared `Overlay` and `openContextMenu()` (DESIGN.md §9.3).

#### Preloading the next track

Load the next track shortly before the current one ends, for gapless changes.
- **Seam:** `PlaylistPlayer` (DESIGN.md §8); crossfades already start the next voice early (§8.4).

#### Committed browser smoke tests

The UI and `WebAudioEngine` have been checked by driving the real page in headless Chromium over the DevTools protocol, using only Node's built-in `WebSocket`. That script lives outside the repository.

- **Notes:** commit it (for example as `scripts/browser-smoke/` with an `npm run smoke` script) so the checks can be repeated. It needs a local Chromium and stays out of `npm run check`. See [`TESTING.md`](TESTING.md). It becomes more valuable as the dialogs add UI.

#### Media element reuse for Safari (only if needed)

New media elements are assumed to play in Safari once the audio context has been unlocked (DESIGN.md §12). If manual testing shows otherwise, `WebAudioEngine` could create a small pool of elements during a click and reuse them.

### Finally: design the remaining features

Once features 6–13 are done, write proposals for everything still open: the three items below and the "Later, unordered" entries above.

#### Mobile design

Make the page usable on a phone or tablet.

- **Changes:** DESIGN.md §1.1 currently targets desktop browsers only, with "no special handling" for touch, and §9 lays the page out for a laptop screen.
- **Notes:**
  - The header's three volume controls collapse into a hamburger menu on narrow screens. Today they have a fixed width and make the page scroll sideways below about 1030 px.
  - The footer's three bars per row, the tile grid and the dialogs need narrow layouts.
  - Context menus need a touch gesture (see "Context menus on touch screens" above).
  - Audio unlocking and playback in Safari on iOS need checking.

#### Remote control

A version of the app that controls another instance running elsewhere: a phone chooses what plays, while the PC does the playing. This expands "LAN access and phone remote control" above.

- **Notes:**
  - It is likely to be used mostly on a phone, so it builds on the mobile design.
  - Open: whether the remote is a separate page or a role of the same page. Today every open tab is an independent player, so the proposal must say which tab is the player and what happens when a second player connects.

#### Loose ends from earlier discussions

- **Customizable playlist looping.** `PlaybackRules.playlistLooping` is always on "for now" (DESIGN.md §8.2). An option could let a playlist stop after its last track instead.
- **Files whose duration can't be measured.** Bootstrap stores `"duration": null` for them (DESIGN.md §3.5), but the UI assumes every sound has a duration: the sound dialog leaves out its Start and end section for such a sound, and crossfades skip such tracks. Decide how they should be handled, for example by reading the duration in the browser on first play, or by reporting them at startup like unsupported files.
